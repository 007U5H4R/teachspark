## Row notes

① **Row 2.** Opening: `.nav__pills` `display:none` → (click) `display:flex`, `aria-expanded` `false`→`true`, 3 links present. Closing again: `display:none`, `aria-expanded` back to `false`. **Defect found:** after closing, `document.activeElement` was `<body>` — a keyboard user who opens the menu, backs out, and is dropped to the top of the document (WCAG 2.4.3). This is **Finding 2**, fixed in this commit — see below.

② **Row 5.** Eye tracking sampled at ~62fps with the window focused, dispatching real `pointermove` to three corners: top-left → `translate(-11.92 7.34)` / `rotateX(-1.54deg) rotateY(-2.71deg)`; bottom-right → `translate(7.96 10.62)` / `rotateX(-2.03deg) rotateY(1.58deg)`; bottom-left → `translate(-13.75 2.63)` / `rotateX(-2.03deg) rotateY(-6.98deg)` — three distinct offsets and tilts. Blink observed in a screenshot (eyes rendered as horizontal bars). CTA hover → `data-state="starry"` confirmed with a **real** mouse hover (not a synthetic `pointerenter`, which does not trigger React's delegated `pointerover`/`pointerout` handler). All five expression shapes are present in the DOM per eye: default, puppy, starry, blink, happy. The "drift idly (touch emulation)" sub-claim specifically was not isolated as a separate observation in the record beyond the code path confirmed in Row 10 (`Spark.tsx:80`'s `window.matchMedia('(hover: hover)')` check, which drives tracking vs. drift and is genuinely width-independent). **Caveat for whoever re-runs this:** an unfocused browser window throttles `requestAnimationFrame` to ~1 frame/600ms, which makes the gaze look frozen when it isn't.

③ **Row 6.** All six visible fields 328×48, full width; submit button 328×52 (≥52 required); Country select shows "India (+91)"; phone prefix chip shows "+91"; honeypot `.hp` computes to `display:none`, box 0×0 (Task 11 fix holding). **Defect found:** the `+91` chip stacked as a full-width 328×22 bar above the 328×48 input at ≤480px — it read as a stray UI artifact rather than a country-code prefix, and was redundant with the Country select immediately above (which already shows "India (+91)"). This is **Finding 1**, fixed in this commit — see below.

④ **Row 8.** The focus indicator on form fields is a lime **border**, not the site-wide lime **outline ring**: `global.css:53` (`.field input:focus, .field select:focus { border-color: var(--lime); outline: none; }`) outranks the global `:focus-visible` rule on specificity, so `outline: none` wins and `border-color` substitutes for it. A visible indicator is present either way, so this **passes** WCAG 2.4.7 — but it looks like a bug when read in isolation (a suppressed outline, with no visible ring anywhere near it). Recorded explicitly so a future pass doesn't "fix" this by removing the `outline: none` and accidentally doubling up the indicator.

## Findings / fixes applied

### Finding 1 — the +91 country-code chip stacked as a full-width bar at ≤480px (FIXED, browser-verified)

`web/src/styles/global.css:91`, inside `@media (max-width: 480px)`, set `.phone { grid-template-columns: 1fr; }`, overriding the base `auto 1fr` (`global.css:56`) and forcing the chip onto its own full-width row above the input.

**Fix:** the override was deleted, restoring `grid-template-columns: auto 1fr` at every width. The `@media (max-width: 480px)` block still contains the unrelated `.hero__title` rule, so the block itself was kept, not removed.

**Verification:** the controller applied and re-measured this fix directly in the live page **before it was written into the codebase** — chip **64×48**, input **256×48**, row **328×48**, `scrollWidth <= innerWidth` still holds, and the result was confirmed by screenshot to render as the standard side-by-side phone-input pattern. The implementer subagent then applied the identical one-line CSS deletion and confirmed `npm run build:web` still succeeds; the implementer has no browser and did not re-verify the visual result — the controller will re-check that after this commit lands.

### Finding 2 — focus was lost to `<body>` when the nav menu closed (FIXED, unit-tested — not yet browser-verified)

`web/src/components/Nav.tsx`. After opening the pill menu with the ☰ toggle and closing it again, `document.activeElement` became `body` instead of returning to the toggle — a keyboard user who opens the menu, decides against it, and closes it was dropped back to the top of the document and had to Tab through everything again (WCAG 2.4.3, Focus Order).

**Fix (implementer subagent):** the toggle button now holds a ref. Two distinct close paths exist instead of a boolean flag:
- `close()` — used by the three nav-link `onClick`s. Leaves focus untouched, since a link click is navigating away and reclaiming focus would fight that navigation.
- `closeAndRefocus()` — used by the toggle's own `onClick` when it closes the menu, and by a new `onKeyDown` handler on the `<nav>` element that closes the menu and refocuses the toggle on `Escape` (while the menu is open). Escape support did not exist before this fix; it was added because it is the realistic trigger for this exact bug — a keyboard user who tabs into the open menu and presses Escape to back out needs focus to land somewhere, and the toggle is the correct place per the WAI-ARIA disclosure pattern.

**Tests added** (`web/test/Nav.test.tsx`, 3 new `it` blocks in the existing `describe('Nav', …)`):
1. `returns focus to the toggle when the toggle closes the menu` — opens the menu, moves focus onto a pill link (simulating a keyboard user tabbing in), then closes via a bare `fireEvent.click` on the toggle (deliberately **not** `userEvent.click`, since `userEvent.click` simulates the browser's own focus-on-click and would pass even without the fix — see "Testing note" below) and asserts `document.activeElement` is the toggle.
2. `returns focus to the toggle when Escape closes the menu` — same setup, closes via `userEvent.keyboard('{Escape}')`, asserts the same.
3. `leaves focus on the clicked link when a nav link closes the menu` — opens the menu, clicks a pill link, asserts focus stays on the link (the fix must not overreach into the link-driven path).

**Testing note (why `fireEvent.click` and not `userEvent.click` for test 1):** `userEvent.click` on a `<button>` simulates the DOM's default focus-on-click behavior, which made an early version of this test pass identically against the pre-fix code — it wasn't exercising the fix at all. Switching the closing click to a bare `fireEvent.click` (which dispatches only a `click` event, with none of `userEvent`'s mousedown-driven default focus) isolates the explicit `toggleRef.current.focus()` call the fix adds. Confirmed genuinely RED against the pre-fix `Nav.tsx` (both new discriminating tests failed with the pre-fix component temporarily restored via `git stash`) and GREEN against the fix — see the implementer's report for the full transcript.

**Not yet verified:** this fix is presently proven only in jsdom. The implementer has no browser and did not attempt to reproduce the original real-Chrome defect or re-check it post-fix; the controller will do that after this commit.
